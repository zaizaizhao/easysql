Langfuse 中的 OpenTelemetry 到底是什么？

用 15 分钟建立一张不混淆的地图：OpenTelemetry 负责“标准化地产生、关联和搬运遥测数据”， Langfuse 负责“存储、呈现和分析 LLM Trace，并连接 Prompt、Score、Dataset 与 Experiment”。

文档核实日期：2026-07-25。示例以 Langfuse v4 OTLP ingestion 和当前 OpenTelemetry 官方文档为准。

先给结论

可以接入其他观测平台，但不是 Langfuse 自动把数据转发出去。 正确做法是让一个共享 OpenTelemetry TracerProvider，或更常见的 OpenTelemetry Collector， 将同一批 Span 分别导出到 Langfuse 与 Grafana Tempo、Jaeger、Datadog、Honeycomb 等后端。

OpenTelemetry

厂商中立的 API、SDK、语义约定、上下文传播、OTLP 协议和 Collector。它不是数据库，也不提供最终分析 UI。

Langfuse

LLM 工程后端：接收 Trace，并提供 LLM 输入输出、Token、成本、Prompt、Score、Dataset、Experiment 等能力。

其他 APM

Tempo、Jaeger、Datadog 等更擅长 HTTP、数据库、队列、微服务拓扑、错误率和基础设施问题。

一个 Trace 是怎样拼出来的

Trace ID: 4bf92f3577b34da6a3ce929d0e0e4736

POST /reviews                         span_id=1111  parent=None
├── load-document                    span_id=2222  parent=1111
├── OCR service                      span_id=3333  parent=1111
├── retrieve-policy                  span_id=4444  parent=1111
├── LLM document review              span_id=5555  parent=1111
└── save-review-result               span_id=6666  parent=1111

每个 Span 有自己的 Span ID，但共享 Trace ID；parent_span_id 形成树。 当 API 调用另一个服务时，默认 W3C Trace Context 将这些信息编码在 HTTP traceparent 中： 

traceparent:
00-4bf92f3577b34da6a3ce929d0e0e4736-1111111111111111-01
不要把 Langfuse Secret Key、文档正文或敏感身份信息放进 traceparent 或 baggage。 Trace Context 需要跨服务传播；Baggage 也可能传播到多个系统。只传安全、低敏、必要的关联字段。

Langfuse 为什么会出现 OpenTelemetry

当前 Langfuse Python SDK v3+ 与 JS SDK v4+ 构建在 OpenTelemetry 之上。 初始化 Langfuse 时，它默认在全局 TracerProvider 上注册 LangfuseSpanProcessor。Langfuse 的 LangfuseSpan、 LangfuseGeneration 和 start_as_current_observation() 是对原生 OTel Span 的 LLM 友好包装。

CallbackHandler 或
Langfuse Client
→
OTel Span
Trace ID · Span ID · Attributes
→
LangfuseSpanProcessor
过滤与 Langfuse 属性映射
→
Langfuse OTLP Backend

这也解释了上一课中的两种写法为何可以嵌套：

with langfuse.start_as_current_observation(
    as_type="span",
    name="document-review-request",
):
    # 普通业务步骤：Langfuse 原生 Observation
    ...

    # LangGraph 内部：CallbackHandler 把回调事件转换为 OTel Span
    await graph.ainvoke(
        state,
        config={"callbacks": [langfuse_handler]},
    )

二者最终都进入 OTel Context，因此新 Span 会自动成为当前活动 Span 的子节点。

能否同时接入其他观测平台？三种模式

模式数据关系适合主要代价
共享 TracerProvider 多个 SpanProcessor 都能看到同一批 Span 单个 Python/Node 服务，希望跨平台保持同一父子树 要处理初始化顺序、过滤、脱敏和重复计费
Collector 扇出 应用只发一次 OTLP，Collector 分发多个后端 微服务、Kubernetes、需要集中重试/过滤/路由 增加 Collector 运维和敏感数据治理责任
隔离 TracerProvider Langfuse 与其他 APM 各自生成/导出 Span 只想让 LLM 数据进入 Langfuse，强隔离优先 跨 Provider 父子关系可能断裂或显示为 orphan

示例 A：共享 TracerProvider，同时发 Langfuse 和 APM

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import (
    BatchSpanProcessor,
)
from opentelemetry.exporter.otlp.proto.http.trace_exporter import (
    OTLPSpanExporter,
)
from langfuse.opentelemetry import LangfuseSpanProcessor

provider = TracerProvider()

# 默认重点导出 Langfuse SDK、gen_ai.* 和已知 LLM instrumentation Span
provider.add_span_processor(LangfuseSpanProcessor())

# 另一个 APM 接收标准 OTLP Trace
provider.add_span_processor(
    BatchSpanProcessor(
        OTLPSpanExporter(
            endpoint="https://your-apm.example/v1/traces",
        )
    )
)

trace.set_tracer_provider(provider)
所有 SpanProcessor 都会看到 Span，但各自能否导出由过滤规则决定。 如果另一个工具先锁定或替换了全局 TracerProvider，后初始化的 Langfuse 可能收不到数据； 生产环境应集中管理 Provider，而不是让多个库各自“抢”全局配置。

示例 B：Collector 将 Trace 双写 Langfuse 与 Tempo

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    limit_mib: 512
    spike_limit_mib: 128
    check_interval: 5s
  batch:

exporters:
  # Langfuse 当前只支持 OTLP over HTTP ingestion
  otlphttp/langfuse:
    endpoint: "https://cloud.langfuse.com/api/public/otel"
    headers:
      Authorization: "Basic ${LANGFUSE_AUTH_STRING}"
      x-langfuse-ingestion-version: "4"

  # Tempo 示例使用 OTLP/gRPC
  otlp/tempo:
    endpoint: "tempo:4317"
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp/langfuse, otlp/tempo]
这是展示“双写机制”的最小配置，不应原样用于生产。它会把 HTTP、SQL、Redis 等所有 Span 都送入 Langfuse。Langfuse 文档说明每个进入的 Span 都可能成为计费 Observation。 生产中要过滤，但必须保留 root 和必要祖先，否则 LLM 子 Span 会变成不完整或孤立 Trace。

哪些东西可以互通，哪些不能

数据/能力能否靠通用 OTel 互通说明
Trace ID、Span ID、父子关系、耗时、错误可以是 OTel Trace 的核心结构。
HTTP、数据库、消息队列调用可以使用标准 instrumentation 和 semantic conventions。
LLM 模型、Token、输入输出有条件依赖 GenAI semantic conventions 或 Langfuse 属性映射；约定仍在演进。
Langfuse Prompt Version 原生关联不能自动保证需要 Langfuse SDK/属性；其他 APM 通常只把它当普通 attributes。
Score、Dataset、Experiment、Annotation Queue不能这些是 Langfuse 应用层领域对象，不是 OTel 信号。
OTel Metrics 与 Logs 进入 Langfuse不要假定Langfuse 当前原生 OTLP 页面承诺的是 Trace ingestion；指标和日志应另接专用后端。
同一 Trace 在 Tempo 与 Langfuse 中可以共享 Trace ID 和父子结构，但“看起来一样”不等于“能力一样”： Tempo 更像分布式系统追踪后端；Langfuse 会把 LLM Span 解释成 Generation，并连接 Prompt、Score 和评测工作流。

Langfuse OTLP 接入的当前协议边界

  • 入口：/api/public/otel，signal-specific 入口为 /api/public/otel/v1/traces。
  • 认证：Basic Auth，内容来自 Project 的 Public Key 与 Secret Key。
  • 实时 v4 ingestion：添加 x-langfuse-ingestion-version: 4。
  • 编码：支持 OTLP/HTTP 的 HTTP/JSON 和 HTTP/protobuf。
  • 当前不支持直接以 OTLP/gRPC 向 Langfuse ingestion endpoint 发送 Trace。
  • Collector 可以 gRPC 接收应用数据，再用 otlphttp exporter 发给 Langfuse。

多部门、多 Project 时怎样套用

部门隔离要发生在“选择 exporter/client”这一层，而不是 Trace Context 层：

认证后的 department_id
    ├── finance → Finance Langfuse client / Project credentials
    └── legal   → Legal Langfuse client / Project credentials

每个请求内部：
    Trace Context 只负责 trace_id、span_id、parent_id
    Project Runtime 负责 public_key、secret_key、Langfuse exporter
  • 不要把 Project Secret Key 放进 OTel attributes、baggage 或 traceparent。
  • 如果通过 Collector 路由多个部门，要为每个目标 Project 配置独立认证 exporter，并用可信的服务端属性路由。
  • 不能信任用户请求体直接提交的 department_id；必须来自认证后的授权上下文。
  • 如果自己的缓存保存 Prompt，缓存键必须包含 Project/部门，不能只用 Prompt name。
  • 跨平台脱敏要分别配置；Langfuse 的 masking hook 不会自动修改另一个 exporter 收到的副本。

文档审核项目的推荐组合

Langfuse 接收

审核 workflow、Prompt version、LLM generation、Token、成本、结构化结果、Score 和人工反馈。

Tempo / Datadog 接收

HTTP、OCR 服务、数据库、Redis、队列、网络错误、服务拓扑和基础设施耗时。

Collector 负责

批处理、重试、内存限制、敏感字段过滤、采样和多后端路由。

对敏感文档，推荐“元数据默认允许、正文默认拒绝”：记录 document_id、长度、类型、模型、Prompt version、 审核分类和哈希；除非明确批准，不把原文、合同条款、人事信息和完整模型输出复制到两个观测平台。

30 秒自测

1. OpenTelemetry 是 Trace 数据库吗？

不是。它提供产生、关联、处理和导出遥测数据的标准与工具；存储和查询由 Langfuse、Tempo、Jaeger、Datadog 等后端负责。

2. Langfuse 接入 OTel 后，会自动把已存 Trace 转发给 Tempo 吗？

不会。应在应用的 TracerProvider 或 OpenTelemetry Collector 层配置第二个 exporter，让同一批 Span 同时进入两个后端。

3. 两个后端能共享什么，不能共享什么？

可以共享 Trace/Span 结构和标准 attributes；Prompt、Score、Dataset、Experiment 等 Langfuse 领域能力不会通过通用 OTel 自动迁移。

4. 为什么不能把所有自动插桩 Span 都发给 Langfuse？

会产生噪声、敏感数据暴露和 Observation 计费；过滤时又必须保留 root 与必要父 Span，避免形成孤立 Trace。
