Prometheus 是做什么的？它和 Langfuse 有什么区别？

Prometheus 负责回答“系统整体现在是否健康、趋势是否异常、要不要报警”； Langfuse 负责回答“具体哪次 LLM 请求出了问题、用了哪个 Prompt、模型为何产生这个结果”。 两者观察的是同一个系统的不同层次，不是替代关系。

文档核实日期：2026-07-25。内容依据当前 Prometheus 与 Langfuse 官方文档。

一句话建立正确心智模型

Prometheus：数字趋势

定时采集带标签的数值时间序列，用 PromQL 聚合，用规则触发告警。 典型问题是错误率、吞吐量、P95 延迟、CPU、连接池和队列深度。

Langfuse：单次 LLM 执行

保存 Trace、Observation、Generation、Prompt、输入输出、Token、成本和 Score。 典型问题是某次审核用了哪个 Prompt，在哪个步骤失败，输出为什么不合格。

OpenTelemetry：共同管道

标准化产生和传输 traces、metrics、logs。它可以把指标送往 Prometheus 体系， 把 LLM Trace 送往 Langfuse，但自身不是最终分析后端。

Prometheus 发现“面上异常” · Langfuse下钻“点上原因” · Trace ID 负责把两层关联起来

  1. 应用或 exporter 在 HTTP /metrics 暴露当前指标。
  2. Prometheus 按固定周期主动拉取这些指标，并写入时间序列数据库。
  3. PromQL 对窗口内的序列做速率、比例、分位数和多维聚合。
  4. Grafana 通常用来画大盘；Prometheus 规则发现异常后将告警交给 Alertmanager 路由。
它尤其适合值班与 SRE 场景。 例如“最近 5 分钟审核错误率是否超过 5%”“某部门队列是否堆积”“P95 响应是否超过 60 秒”。

工程中最常见的四类指标

类型含义文档审核示例常见查询方式
Counter 只增加或重置的累计值 document_review_requests_total、llm_tokens_total 对它使用 rate() 求每秒速率
Gauge 可以上升也可以下降的当前值 document_review_queue_depth、active_review_jobs 当前值、最大值、平均值
Histogram 将观测值分桶，保留 count 与 sum document_review_duration_seconds、llm_request_duration_seconds 跨实例聚合后计算 P95 / P99
Summary 客户端计算滑动窗口分位数 少数客户端本地延迟统计 分位数通常不适合跨实例直接聚合

Web 服务最基本的一组信号经常概括为 Rate Errors Duration； 再补上资源饱和度、队列积压和依赖健康度。

Prometheus 和 Langfuse 的核心区别

维度PrometheusLangfuse
基本数据单元 一个数值时间序列样本 Trace / Observation / Generation / Score
主要问题 整体是否异常？何时开始？影响多大？ 具体请求做了什么？Prompt 和输出是什么？为什么失败？
数据内容 数值、时间戳和低基数 labels 调用树、输入输出、模型、Token、成本、Prompt version、元数据
查询与呈现 PromQL、recording rules、Grafana Langfuse UI、Public API、Metrics API
告警 成熟的规则评估和 Alertmanager 生态 重点是 LLM 追踪、评测、人工标注和质量分析
Prompt 生命周期 不管理 Prompt Prompt 版本、labels、trace 关联和实验对比
质量评测 可保存聚合后的业务指标，但不了解评测语义 Score、Dataset、Experiment、人工/模型评测
高基数明细 应避免；会造成时间序列爆炸 Trace ID、Session ID、请求元数据是其正常查询维度

你的多部门文档审核项目：数据应该怎样分工

放进 Prometheus

  • 每秒审核请求数、成功数、失败数
  • 端到端和 LLM 调用 P50 / P95 / P99 延迟
  • 待审核队列深度、运行中任务数、worker 饱和度
  • API、数据库、OCR、向量库错误率
  • CPU、内存、磁盘、连接池和进程存活
  • 按模型聚合的 Token 速率或预算消耗趋势

放进 Langfuse

  • 某次文档审核的完整调用树
  • 使用的 Prompt 名称、版本和实际编译结果
  • LLM 输入输出、模型、Token 与成本
  • 检索、规则检查、生成、复核各步骤耗时
  • 审核正确率、完整性、风险漏检等 Score
  • bad case、人工纠正、Dataset 与 Experiment
# Counter：department 和 result 都是有限枚举
document_review_requests_total{
  department="finance",
  result="success"
} 18352

# Gauge：当前队列深度
document_review_queue_depth{department="legal"} 47

# Histogram：客户端会产生 _bucket、_sum、_count 序列
document_review_duration_seconds_bucket{
  department="legal",
  le="30"
} 912

三个真正有用的 PromQL 示例

1. 最近 5 分钟各部门每秒审核量

sum by (department) (
  rate(document_review_requests_total[5m])
)

2. 最近 5 分钟各部门错误率

sum by (department) (
  rate(document_review_requests_total{result="error"}[5m])
)
/
sum by (department) (
  rate(document_review_requests_total[5m])
)

3. 各部门审核 P95 延迟

histogram_quantile(
  0.95,
  sum by (department, le) (
    rate(document_review_duration_seconds_bucket[5m])
  )
)

Histogram bucket 要按 le 保留后再传给 histogram_quantile()；实际 bucket 边界应按你的审核时长分布配置。

最重要的坑：不要把请求 ID 做成 Prometheus Label

Prometheus 中“指标名 + 全部 label 值”唯一确定一条时间序列。 每个新 document ID 或 trace ID 都会创建新序列；这会快速放大内存、磁盘和查询成本。

适合做 label不要做 label明细应该放哪里
有限的 department、environment、route trace_id、request_id、session_id Langfuse Trace metadata 或日志
status、provider、有限模型名 document_id、用户名、邮箱、文件名 业务数据库或受控 Trace 元数据
受控错误码，例如 timeout、rate_limit 完整错误文本、Prompt、文档正文、模型输出 脱敏后的 Langfuse / 日志系统
安全与性能是同一个结论： 文档正文、Prompt、模型输出和身份信息都不应进入 Prometheus labels。 即使写入 Langfuse，也要先做权限隔离、数据最小化与脱敏。

相同 trace_id

正确做法是使用 exemplar：它给某个 Histogram 样本附加一个代表性 trace_id，Grafana 等前端可以从延迟尖峰跳到具体 Trace。 它不会像普通 label 那样为每个 trace ID 建立永久时间序列。

Exemplar 只提供“代表性样本”，不是每次请求的精确索引。 精确逐请求审计仍应查询 Langfuse、日志或业务数据库。

Langfuse 也有 Metrics，为什么还要 Prometheus？

Langfuse 的 Metrics API 可以从已经采集的 Observation 和 Score 中聚合成本、Token、 延迟、调用量和质量分数；所以“LLM 成本趋势”“某 Prompt version 的平均 Score” 可以直接在 Langfuse 分析。

但它不是 Prometheus 的通用替代品：官方 Metrics API 是针对 Langfuse 数据模型的分析接口， 而 Prometheus 提供通用时间序列采集、PromQL、recording/alerting rules，以及覆盖主机、 容器、数据库、队列和任意服务的 exporter 生态。

你要问的问题优先工具
LLM 调用量、Token、成本、延迟是否按天上涨？两者都能聚合；Langfuse 上下文更丰富
Prompt v12 是否比 v11 的完整性 Score 更好？Langfuse
API P95、数据库连接池、CPU 和队列是否异常？Prometheus
凌晨错误率超过 5% 时通知值班群？Prometheus rules + Alertmanager
某次审核为什么错误、输入输出是什么？Langfuse

边界：Prometheus 不适合做什么

  • 不适合保存 Prompt、文档正文、完整异常栈或逐请求业务对象。
  • 不适合依赖无限基数 labels 做逐用户、逐文档、逐 Trace 查询。
  • 不保证每个事件都适合作为精确账单或法务审计记录；Prometheus 官方也不建议把它用于要求 100% 准确性的逐请求计费。
  • 它不是日志系统，也不是完整的分布式 Trace 后端；通用日志可用 Loki/ELK，通用 Trace 可用 Tempo/Jaeger。

30 秒自测

1. Prometheus 已发现“法务部 P95 审核耗时升到 90 秒”，下一步去哪找原因？

用 exemplar 或共享 trace ID 下钻 Langfuse，查看具体请求的 OCR、检索、LLM 和复核步骤，以及 Prompt、模型和输出。

2. 为什么不能把 document_id 放进 Prometheus label？

每个不同 label 组合都会创建新时间序列；逐文档 ID 会导致高基数和序列爆炸。它应进入 Langfuse metadata、日志或业务数据库。

3. Langfuse 有 Metrics API 后，Prometheus 是否多余？

不多余。Langfuse 聚合其 LLM Trace 与 Score；Prometheus 负责整个工程的通用指标采集、PromQL、告警和基础设施生态。

4. 多部门场景能否把 department 做成 label？

如果部门来自服务端认证上下文且数量有限、稳定，通常可以；不要接受任意用户输入，也不要把部门名称扩展成无限动态值。
