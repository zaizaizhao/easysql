Lesson 0001 · EasySQL

用 Langfuse 建立 bad case → Prompt 迭代闭环

目标不是“把 Langfuse 接上”，而是让每次 Prompt 修改都能回答三个问题： 修复了哪些失败？引入了哪些回归？是否可以安全晋级到 production？

调研基线：2026-07-13；Langfuse Python SDK 当前 PyPI 版本为 4.14.0。

先给结论

EasySQL 已经有 Langfuse tracing 的起点，但尚未形成质量闭环。当前集成能看调用链、模型耗时和 SQL Agent span； 缺少的是 Prompt version 关联、Dataset、Experiment、结构化 Score、人工反馈入口和 Text2SQL 专用判分器。

Langfuse 应负责

Trace、Prompt 版本、Dataset、Experiment run、Score、人工审核、比较和 label 发布。

EasySQL 应负责

执行 SQL、结果集等价、Schema Linking、业务约束、失败分类、只读沙箱和发布门禁规则。

最重要的原则

Langfuse 是实验与证据平台，不是 Text2SQL 正确性判分器，也不会自动保证 Prompt 变好。

完整闭环

生产 Trace / 离线失败
→
Score + 人工审核
→
回归 Dataset
→
Prompt 候选版本
Experiment 回归
→
基线对比与门禁
→
production label
→
继续监控并收集失败

这里的关键不是“一轮只跑 bad case”。候选 Prompt 至少要跑核心 golden set 和历史 bad-case regression； 发布前再跑一个优化过程中不可见的 holdout，避免为了修 10 条失败而破坏另外 50 条。

EasySQL 当前代码处于哪里

位置当前行为缺口
easysql/llm/agent.py 创建 Langfuse LangChain CallbackHandler。 handler 被 QueryService 缓存复用；没有固定每轮 trace_id，也没有 Prompt version。
easysql_api/services/query_service.py 把 callback、session_id 和 text2sql tag 挂到 LangGraph config。 没有反馈接口、trace_id 持久化、Dataset 关联和评测运行模式。
easysql/context/templates.py SQL 生成 Prompt 硬编码在代码中。 无法在 Langfuse 中版本化、按 label 部署或回滚。
easysql/llm/nodes/sql_agent.py SQL Agent 有手写 span，记录 SQL、是否通过验证和迭代次数。 有效 Prompt 由两段系统指令拼接，未绑定 Prompt object；工具失败原因未统一评分。
easysql/llm/nodes/validate_sql.py 通过 EXPLAIN 或语法检查判断 validation_passed。 它不能证明业务语义正确，不能作为 Experiment 的唯一 accuracy。
easysql/llm/nodes/retrieve_few_shot.py 从 Milvus 检索已确认的问答示例，注入运行时 Prompt。 这是 Few-shot 库，不是评测 Dataset；不要把错误 SQL 直接放进去。
依赖版本需要先修正。 requirements.txt 目前写的是 langfuse>=2.0.0， 但代码已经使用 get_client、start_as_current_observation 和当前 CallbackHandler 接口。 2026-07-13 的 SDK 最新版本是 4.14.0，且 v4 在 2026 年 3 月重写。 实施前应显式约束主版本，例如 langfuse>=4.14.0,<5.0.0，并跑兼容测试。

Langfuse 数据模型如何映射到 Text2SQL

对象EasySQL 中的角色设计要点
Trace一轮用户问题到最终 SQL 的完整执行用 session_id + message_id 生成确定性 trace_id，便于前端反馈。
Observationretrieve、build_context、generation、validate、execute输出结构化字段，不只保留日志字符串。
Prompt VersionSQL 生成或 SQL Agent 的不可变提示词版本Experiment 固定 version；生产只读 production label；不用 latest。
Dataset Item一个问题、一个数据库快照和一组期望证据expected_output 不应只有 SQL 文本，还要有结果、表、过滤条件和澄清预期。
Experiment Run某一固定配置在整个数据集上的回归执行记录 dataset version、prompt version、model、retrieval hash、git SHA。
Score每条 case 或整轮 run 的质量度量Boolean/Numeric/Categorical/Correction/Text 分开建模。

Dataset 应怎样设计

建议先建三个数据集，而不是把所有东西塞进一个“测试集”：

easysql-golden-core

30～100 条长期稳定、覆盖核心业务能力的人工确认样本。

easysql-badcase-regression

从生产或历史实验中筛出并完成纠正的失败案例。

easysql-holdout

优化 Prompt 时不查看，发布前才跑，用来识别过拟合。

Langfuse v4 支持为 Dataset 设置 input_schema 和 expected_output_schema，建议直接用 JSON Schema 约束字段：

from langfuse import get_client

langfuse = get_client()

langfuse.create_dataset(
    name="easysql-badcase-regression",
    description="Curated Text2SQL production regressions",
    input_schema={
        "type": "object",
        "required": ["case_id", "question", "db_name"],
        "properties": {
            "case_id": {"type": "string"},
            "question": {"type": "string"},
            "db_name": {"type": "string"},
            "dialect": {"type": "string"},
            "conversation_history": {"type": "array"},
        },
    },
    expected_output_schema={
        "type": "object",
        "properties": {
            "reference_sql": {"type": "string"},
            "expected_tables": {"type": "array", "items": {"type": "string"}},
            "required_filters": {"type": "array", "items": {"type": "string"}},
            "expected_result_digest": {"type": "string"},
        },
    },
)

原始 thumbs-down 不应立即进入正式 regression dataset。先写 Score 并进入 Annotation Queue； 只有审核人补齐 failure_category、正确 SQL 或正确结果后，才晋级为回归样本。 否则测试集会充满“知道错、但不知道正确答案”的脏标签。

Score：不要只看 validation_passed

建议把质量拆成四层，每层回答不同问题：

层指标判分来源
L1 可运行syntax_valid、execution_valid、read_only_safeSQLAlchemy / 数据库沙箱
L2 语义正确result_equivalent、required_filters、business_constraints结果集比较器 + 规则
L3 检索正确table_recall、column_recall、join_path_coverage、noise_rateretrieval_result 与 expected schema
L4 成本效率latency、token、tool_calls、retry_countTrace / Agent artifact
 
from langfuse import Evaluation

def text2sql_evaluator(*, output, expected_output, **kwargs):
    result_ok = compare_result_sets(
        generated=output["execution_result"],
        expected_digest=expected_output["expected_result_digest"],
    )
    expected_tables = set(expected_output.get("expected_tables", []))
    retrieved_tables = set(output.get("retrieved_tables", []))
    table_recall = (
        len(expected_tables & retrieved_tables) / len(expected_tables)
        if expected_tables
        else 1.0
    )

    return [
        Evaluation(
            name="execution_valid",
            value=bool(output["execution_valid"]),
            data_type="BOOLEAN",
        ),
        Evaluation(
            name="result_equivalent",
            value=result_ok,
            data_type="BOOLEAN",
        ),
        Evaluation(name="table_recall", value=table_recall),
        Evaluation(
            name="failure_category",
            value=classify_failure(output, expected_output),
            data_type="CATEGORICAL",
        ),
    ]

Prompt Management 的正确接入 seam

不建议在每个 Graph node 里散落 get_prompt 调用。应建立一个深模块，例如 easysql/prompts/，用很小的 interface 隐藏缓存、fallback、label/version、SDK 对象、 LangChain metadata 和可观测性关联。

PromptRuntime interface

resolve(role, variables, selector) → 编译后的 messages + 可序列化 PromptRef。

Langfuse adapter

通过 name/version/label 获取 Prompt，处理 cache、fallback、PromptClient 和追踪关联。

Local adapter

测试和 Langfuse 不可用时使用代码内模板；同一 interface，不让调用方感知外部 SDK。

PromptRef 必须可序列化，因为它会进入 LangGraph state；PromptClient 只能短暂存在于调用进程内：

from dataclasses import dataclass
from typing import Any

@dataclass(frozen=True)
class PromptRef:
    name: str
    version: int
    labels: tuple[str, ...]
    is_fallback: bool

@dataclass(frozen=True)
class RenderedPrompt:
    messages: list[dict[str, Any]]
    ref: PromptRef

class PromptRuntime:
    def resolve(
        self,
        *,
        role: str,
        variables: dict[str, Any],
        version: int | None = None,
        label: str | None = None,
    ) -> RenderedPrompt:
        ...

    def attach_to_runnable_config(
        self,
        *,
        ref: PromptRef,
        config: dict[str, Any] | None,
    ) -> dict[str, Any]:
        ...

当前 BuildContextNode 和 GenerateSQLNode 是分开的。不要把 PromptClient 放进 context_output。 可以在 build_context 中保存 PromptRef 和已编译文本，在 generation 中按 PromptRef.version 从缓存重新获取精确 PromptClient； 或在后续重构中把最终 Prompt 编译收口到 generation module。
Agent Mode 与 Legacy Mode 的有效 Prompt 不相同。Agent Mode 还拼接了工具使用、强制验证和迭代规则。 应分别管理 easysql/sql-agent-generation 与 easysql/sql-generation，不能用同一个版本号假装它们是同一实验变量。

Trace：每一轮都要有稳定 ID

QueryService 当前缓存 CallbackHandler。CallbackHandler 本身保存 run map、prompt map 和 last_trace_id； 复用至少会让“这一轮对应哪个 trace_id”难以可靠读取。建议每轮创建新 handler，并提前生成确定性 trace_id： 

from langfuse import get_client
from langfuse.langchain import CallbackHandler

def make_langfuse_run_config(
    *,
    session_id: str,
    message_id: str,
    thread_id: str,
) -> tuple[dict, str]:
    langfuse = get_client()
    trace_id = langfuse.create_trace_id(
        seed=f"easysql:{session_id}:{message_id}"
    )
    handler = CallbackHandler(trace_context={"trace_id": trace_id})

    config = {
        "configurable": {"thread_id": thread_id},
        "callbacks": [handler],
        "metadata": {
            "langfuse_session_id": session_id,
            "langfuse_tags": ["text2sql"],
            "message_id": message_id,
        },
    }
    return config, trace_id

随后把 trace_id 持久化到 Turn 或 Message，这样前端 thumbs-down、SQL 编辑和人工审核都能精确回写到同一 Trace。

Experiment Runner：不要通过在线 HTTP 绕一圈

建议建立 easysql/eval/ 深模块，直接调用 graph。它的 interface 可以只有 run(spec) → EvaluationReport，内部隐藏 Langfuse Dataset、并发、Trace、SQL 沙箱、判分和报告。

Langfuse Experiment runner 会自动创建 Dataset Run、追踪 task、把结果连接到 Dataset Item，并支持同步或异步 task/evaluator。 EasySQL 只需要让 task 返回足够完整的结构化 artifact。

如何根据 bad case 优化 Prompt

  1. 先分类根因。 WRONG_TABLE、MISSING_COLUMN 更可能是 retrieval；WRONG_JOIN、MISSING_FILTER 可能是 Prompt 或上下文；DIALECT_ERROR 可能是数据库规则；不要把所有失败都归因于 Prompt。
  2. 形成最小修复假设。 例如“模型漏掉状态过滤，是因为 Prompt 没要求显式核对业务状态字段”。
  3. 创建不可变候选版本。 写清 commit_message，不直接覆盖 production。
  4. 先跑失败子集。 快速验证修复假设是否成立。
  5. 再跑 core + regression。 确认没有广泛回归。
  6. 最后跑 holdout。 防止针对已知 bad case 过拟合。
  7. 通过门禁后晋级。 把 production label 移到候选 version；保留旧版本用于一键回滚。
candidate = langfuse.create_prompt(
    name="easysql/sql-agent-generation",
    type="chat",

    labels=["candidate"],

        "temperature": 0,
        "query_mode": "plan",
        "use_agent_mode": True,
    },
    commit_message="Require explicit verification of business status filters",

# Experiment 必须使用 candidate.version，而不是 candidate/latest label。
run_candidate_experiment(prompt_version=candidate.version)

Bad case 与 Few-shot 的关系

Bad case 首先是 regression case，用来防止错误再次发生；Few-shot 是运行时上下文，用来影响模型行为。二者可以有关联，但不能自动互转。
  1. 错误输出只进入 Trace、Score 和审核队列，不能进入 Milvus Few-shot。
  2. 审核人提供正确 SQL，样本进入 Langfuse regression dataset。
  3. 如果该正确案例具有代表性、不会泄露敏感信息、且相似检索有帮助，再通过 EasySQL 现有 /few-shot 流程加入 Milvus。
  4. Experiment 应记录本轮实际召回了哪些 Few-shot，避免把 Prompt 改进和 Few-shot 变化混为一谈。

推荐实施顺序

  1. P0：固定 SDK 主版本。 升级并约束 Langfuse v4，补 auth、callback、prompt fetch 和 experiment smoke tests。
  2. P0：稳定 Trace identity。 每轮新建 CallbackHandler，生成并持久化 trace_id。
  3. P1：建立 PromptRuntime 深模块。 先迁移最终 SQL generation/agent Prompt，保留 local fallback。
  4. P1：建立 30～50 条 golden cases。 优先覆盖真实中文业务、JOIN、过滤、聚合、时间和方言。
  5. P1：实现 EvalRunner + result-set comparator。 直接跑 graph，完整保留 retrieval、prompt、tool 和 execution artifact。
  6. P1：接 Langfuse Experiment。 Dataset version + Prompt version + metadata + evaluator + run evaluator。
  7. P2：增加反馈接口和 Annotation Queue。 thumbs-down、失败类别、SQL correction、审核晋级。
  8. P2：加入 CI 发布门禁。 使用 Langfuse Experiment Action 或项目自己的 RegressionError 逻辑。
